# Epic 1 Decisions — Authentication & Role-Based Access

## 1. What technology and repository structure should the project use?

**Chosen answer:** PostgreSQL with a monorepo structure: `apps/web` for Next.js and `apps/api` for ASP.NET Core. The backend uses .NET 10 with Domain, Application, Infrastructure, and API layers.

## 2. How should users authenticate and be authorized?

**Chosen answer:** Use ASP.NET Identity, JWT authentication, and backend-enforced role-based authorization for Admin, Teacher, and Student.

## 3. What identifier should users use to sign in?

**Chosen answer:** Institutional ID and password. Examples are `ADM-001`, `TCH-001`, and `STU-001`. The database uses an internal immutable GUID for relationships. Email is optional contact information, not the login identifier.

## 4. How should the browser receive the authentication token?

**Chosen answer:** Store the JWT in an HttpOnly, SameSite=Strict cookie. Do not store tokens in browser JavaScript or local storage.

## 5. What happens after a successful sign-in?

**Chosen answer:** Redirect by role: Admin to `/admin`, Teacher to `/teacher`, and Student to `/student`. The backend also verifies access to protected endpoints.

## 6. How should account deactivation work?

**Chosen answer:** Admin can deactivate and reactivate accounts. A deactivated user cannot sign in and immediately loses protected API access, while academic history remains preserved.

## 7. How should local development run?

**Chosen answer:** Use Docker Compose for the API and PostgreSQL. PostgreSQL uses host port `5433` because `5432` is already occupied locally. Real local credentials and JWT keys remain in ignored configuration files; only example files are committed.

## 8. What visual direction should the application use?

**Chosen answer:** Use the supplied dark, atmospheric full-site theme and dark login-card direction. A development/demo credential panel may be added later, but never with production credentials.

## 9. What coding architecture rules apply globally?

**Chosen answer:** Apply SOLID, DRY, KISS, and YAGNI. Keep controllers thin. Use Controller → Application Service → Focused Repository → DbContext for substantive business workflows, but do not create generic repositories, pass-through services, or wrappers around framework services merely for pattern compliance.
